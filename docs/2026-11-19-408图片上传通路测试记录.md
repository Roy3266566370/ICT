## 发现并修复的问题（4 处）

### 1. `source_recovery.py` — `assess_text_quality` 误伤答题空括号
图片题面含 `（ ）`（选择题标准答题空）即记"存在孤立括号"→ 判 OCR 不可信 → 跳过本地建模进 `pending_ai`。
**影响**：所有图片选择题（408 单选是主力题型）永远无法走本地内核。
**修复**：空括号仅在公式语境（前一字符为字母/数字/运算符/`_`/`^`/`∫` 等）才记 issue；中文语境与句首的 `（ ）` 视为正常排版；`[]` 空括号保持标记。

### 2. `data_structures.py` — stack_through_queue 题被 queue_ops 抢占
"出栈后立即进入队列"类真题被 `queue_ops` 的 `出队|队列` 模式命中，产出无意义模型（capacity=6, ops=[pop]）。
**修复**：`build_queue_ops` 开头加护栏——出现 `出栈…进入队列` 句式即 `return None`，让位 `stack_ops`。

### 3. `data_structures.py` — stack_ops 不支持字母元素与"依次进栈/出队序"表述
`build_stack_ops` 只认"入栈序列/出栈序列"字面且只解析数字（`_seq` 仅 `-?\d+`）；408 栈题元素惯用 a,b,c,…。
**修复**：
- 新增 `_item_seq`：元素级序列解析（数字或字母/标识符）。
- 新表述模式：`X,X,… 依次进` + `出队（的）顺序是 X,X,…`（或"出栈的顺序是"），建成 `mode=check` 模型。
- 新增 `goal` 字段：题面含"容量至少/栈深/最大深度"时 `goal=capacity`。
- `eval_stack_ops` check 模式跟踪 `max_depth`，`goal=capacity` 时答案给出"栈内最多同时 k 个元素，容量至少为 k"并输出 `answer_value`。

### 4. `heap.py` — 缺失"已给堆中插入单个元素"模式
`build_heap` 只有"删堆顶 N 次"与"依次插入建堆"两种模式；"插入关键字 3"被判为 delete 且丢失插入值 → 因缺 deletion_count 阻塞为 `needs_review`。
**修复**：检测到 `插入\s*(关键字|元素|值)?\s*数字` 且已有 `initial` 堆时，把被插值追加到序列并置 `operation='insert'`。
依据：合法堆按层序逐项重插是不动点（每个元素 ≥ 父节点则不上滤），故"已有堆+插入"等价于"序列重插"，直接复用现有插入内核；`solve_heap` 的 choices 比对自动判出选项 A。

### 5. `recognize.py` — `model_coverage_issues` 裸数字核对误伤序列模型
"题干中的数值全部没有进入模型条件"会把题号/年份/选项标号等噪声数字计入；对元素为字母的栈题必误报 → `pending_ai`。
**修复**：模型已含非空结构化序列字段（push_seq/pop_seq/ops/initial_heap/reference/processes/nodes/edges/requests/allocation/max/available/names）时跳过该项检查。
