## 3 P0 最先处理的事项

### A01 让当前运行服务实际提供账号接口

**现象：** 在当前登录页输入测试邮箱和密码后，`POST /api/v1/auth/login` 返回 404，界面提示“资源不可用”。直连 `127.0.0.1:8000` 和通过前端 5173 代理请求，结果一致。

**已确认的原因范围：** 8000 端口的 `/openapi.json` 中，注册、登录、退出和 `/me` 四条账号路由全部缺失；现有材料与访客会话路由正常存在。

当前后端进程启动时间为 12:18:53，账号路由文件修改时间为 15:12:57；新实例测试可加载账号路由，现象符合旧后端进程未重新加载代码。最终恢复需在修复阶段核对进程对应目录、依赖及重载后的路由。

**需要补充：**

- [ ] 核对运行中的后端版本与目录，重新加载后确认四条账号路由实际存在。
- [ ] 启动检查增加“必需路由完整性”，不能只因为 `/openapi.json` 能访问就认为后端可用。
- [ ] 必需的账号路由导入失败时，应让启动检查失败；不能仅记录 warning 后继续启动一个缺接口的版本。
- [ ] 由真实网页完成成功登录、错误密码、读取账号、退出四种情况。

**验收：** 当前页面登录不再返回路由 404；错误凭据返回明确的 401，正确凭据能够登录并在刷新后保持可识别的账号状态。

证据：[运行服务路由检查](../../../verify/account-home-audit-2026-11-07/running-api-routes.json)、[错误页面截图](../../../verify/account-home-audit-2026-11-07/05-login-error-mobile.png)、[启动脚本](../../../start-dev.ps1)、[路由自动注册](../../../backend/app/api/registry.py)。

### A02 把作品归属从访客会话接到正式账号

**现状：** `materials` 和 `labs` 等记录仍关联 `session_id`。材料授权仍判断 `row.session_id == ctx.session_id`，没有按正式账号或空间授权。当前数据库也没有 `workspaces`、`resources`、`guest_claims` 等规划中的归属表。

**本轮隔离复现：** 同一访客会话中放入一份测试材料，先后登录账号 A 和 B，两次材料列表均返回该份材料；退出账号后，访客 Cookie 仍能访问它。验证范围是同一浏览器访客会话，不是读取任意其他人的材料。

这意味着“登录账号”目前尚未决定“能看哪些作品”，同一账号换设备也没有对应的作品查询依据。

**需要补充：**

- [ ] 建立个人空间与长期资源归属；材料、题目实验、运行和核对记录沿父资源统一授权。
- [ ] 注册激活后创建个人空间，上传和保存写入该空间。
- [ ] 提供“保存当前访客成果”，同时验证账号与访客会话，事务内认领，防止重复和抢领。
- [ ] 账号作品不随访客 24 小时到期；登录会话期限与作品保留期分开。
- [ ] 附件、预览、下载、导出、任务查询和分享管理都执行同一归属判断。
- [ ] 用两账号、两浏览器、退出和会话过期场景验证隔离。

**验收：** 设备 A 的已保存作品能在设备 B 登录同一账号后恢复；切换账号后只显示该账号获准访问的内容；退出账号不能继续用原访客 Cookie 访问已被账号认领的私有作品。

证据：[材料模型](../../../backend/app/db/models.py)、[当前归属判断](../../../backend/app/api/__init__.py)、[隔离复现记录](../../../verify/account-home-audit-2026-11-07/account-boundary-check.log)。授权设计可继续依据 [OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) 的资源授权与逐请求校验原则。

### A05 和 A06 的具体边界

前端客户端已经有账号 API，后续应建立统一的账号状态来源，而不是每个页面自己判断是否登录。

- 首次加载请求 `/me`，处理“恢复中、已登录、访客/未登录、服务不可用”。
- 账号资料与 CSRF 令牌分别管理，原始登录 Cookie 保持由服务端控制。
- 退出时调用真实退出接口，再清理账号状态、私有缓存与当前账号的临时展示数据。
- 401 时保留未提交草稿并引导重新登录，重新登录不同账号后不得自动上传旧账号草稿。
- “访客可以继续体验”和“账号私有空间需要登录”分别处理，不把全部公开页面强制挡在登录前。

### A08 和 A09 的生产门槛

开发模式注册即激活是当前代码明确选择，适用于本地验证。公开接受注册时，需要选择并落实正式验证方案，提供密码恢复和防滥用能力。认证限流、恢复与安全会话管理参考 [OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)。

当前 `SESSION_COOKIE_SECURE=false` 符合本地 HTTP 调试条件；部署 HTTPS 时需显式启用 Secure。当前检查不据此判定本地存在配置故障。

### A10 已确认的数据库比较差异

只读 SQL 比较表明：应用规范化后的 `cafe@example.com` 和 `café@example.com` 不相同，但当前 MySQL 排序规则将它们比较为相等。应用查询和唯一约束可能把不同标识当作同一个登录身份。

建议首版明确采用 ASCII 邮箱本地部分，或为国际化邮箱建立正式规范化规则；在此基础上，为规范化后的标识使用精确比较。不能在未盘点现有数据前直接改整张表的排序规则。`_ai` 的重音不敏感语义见 [MySQL 排序规则说明](https://dev.mysql.com/doc/refman/8.0/en/charset-collation-names.html)。

### A12 已完成基础和仍需补齐的部分

MySQL 接入本身已存在，不需要再次从零搭建。本轮读取的当前配置使用 MySQL 8.0.43，而原规划建议 8.4 LTS；应统一文档、目标版本和持续集成环境，升级另做兼容性评估。

本地账号表迁移版本为 `0001_account_tables`。原业务表仍由 `create_all()` 建立，后续增加归属字段、索引和非空约束时需要正式迁移。当前配置没有独立迁移连接，应在部署阶段拆分应用和迁移权限，并验证配套文件恢复。

## 5 P2 主页与登录页的体验补充

### A13 静态场景不要继续显示暂停动效

390px 宽的登录页首次加载后没有 Canvas，海报已显示，但按钮仍写“暂停动效”。无 WebGL 和性能降级场景也有同类状态表达风险。

- [ ] 动态可用时显示“暂停动效 / 播放动效”。
- [ ] 当前只能静态展示时显示“静态展示”，或隐藏播放控件。
- [ ] 手动暂停、输入暂时冻结和永久静态降级分别表达，避免用户点击一个不会改变画面的控件。

来源：[场景容器](../../../frontend/src/components/auth/LoginSurface.tsx)、本轮移动端截图 04。

### A14 调整三维场景的构图与主题融合

主题颜色已基本一致。当前桌面曲面位于一块可辨识的浅色圆角矩形内，图形在舞台中偏小，舞台占用较大空间，和前面选定的“连续暖纸画布、舒展大曲面”仍有差距。

- [ ] 场景背景与页面背景统一，减少单独卡片感；保留必要的交互按钮。
- [ ] 按右侧容器实际范围调整镜头，让曲面更舒展，同时保留安全边距。
- [ ] 平衡主题标题、说明、装饰线与曲面之间的留白，不通过增加色彩解决尺度问题。
- [ ] 按选定方案补齐弱坐标轴标记，或统一决定简化；不要让静态图和动态场景各用一套表达。

来源：[登录页样式](../../../frontend/src/pages/LoginPage.module.css)、本轮桌面截图 02。

- [ ] 海报、Canvas 保持相同背景、取景、对象位置和观察点状态。
- [ ] 在固定相位下截图比较，避免只用“参数测试通过”代替视觉核对。

### A16 完善真实设备质量档位和异常反馈

目前有质量降级与暂停逻辑，输入暂停和系统减少动效已实测通过。仍需要补充：

- [ ] 按 1024—1279px 的中等宽度设置初始低档质量，不能只等待卡顿才调整。

## 9 建议实施顺序

1. **恢复当前运行接口并加入路由完整性检查。** 先消除网页登录 404。
2. **接入全局登录状态、注册入口和退出入口。** 让新用户可以完成基本账号流程。
3. **建立账号资源归属、访客转存和长期保存。** 在此完成前，不对外承诺跨设备恢复私有作品。
4. **补齐密码恢复、邮箱策略、限流、标识比较与部署迁移。** 形成可对外使用的首版。
5. **打磨曲面构图、静态切换、移动端状态和广泛用户叙述。** 沿用现有品牌配色。
6. **按需求扩展团队、身份偏好与探索分支。** 不让首版被次要功能拖住。
